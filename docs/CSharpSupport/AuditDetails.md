## Audit: names - Test names, listing parser, /select generation, traits, VS names (managed/C# TAEF tests)

Every name-handling path in the adapter assumes C++ names with '::' as the scope separator. Managed names use '.' for every separator, so today the adapter fails at the first step.

**What happens today (measured):** I fed real TE.exe /listProperties output for two C# DLLs into the shipped Release TaefTestAdapter.Core.dll. StreamingListPropertiesParser produced 0 descriptors and 35 and 21 "unexpected lines". Its check that a test line belongs to the current class (StreamingListPropertiesParser.cs:307) requires '\<class\>::', so every managed test line is rejected. Even forcing discovery with a .is_taef_test indicator file would yield zero tests.

**TaefNames misparses managed names:**
- Class names come back empty, so every test lands in class "" and class selection terms are never used.
- It corrupts row names that contain '::': 'Edge.Ns.Rows.M#Weird::Row' becomes the VS FQN 'Edge.Ns.Rows.M#Weird.Row'.

**What already works and needs no change:**
- The listing layout is identical to native (same indentation, Setup:/Property[]/Data[] lines, '#error [Blocked]' pseudo tests). The module-level 'Property[TaefTestType] =  Managed' line arrives before the first class, so the parser can learn per DLL that names are managed.
- Execution output uses the same StartGroup/EndGroup format. The parser matches groups to tests by exact name, which works for any naming.
- /select with dotted class terms works. `(@Name='Contoso.Managed.Tests.BasicTests.*' and not @Name='Contoso.Managed.Tests.BasicTests.*.*')` selected exactly that class's 11 tests (probe).
- The WTT log path does not depend on naming.

**Recommended design (native behaviour stays byte-for-byte identical, so golden files are unaffected):**
1. Add managed variants of TaefNames (new methods or an isManaged flag). The existing single-argument methods stay native-only.
2. The listing parser switches its separator to '.' once it sees Property[TaefTestType]=Managed in the module scope. It resets this on each test DLL line.
3. For managed tests, TestCaseFactory takes the class from the TE.exe listing (descriptor.ClassName), not from re-parsing the name. That makes data-driven classes with named rows containing '.' unambiguous ('Edge.Ns.DataClass#a.b c.InClass').
4. It stores that class in a new managed-only test property, TestCaseTaefClassProperty, round-tripped through a new VS property 'TaefTestAdapter.TaefClass'. Its presence is the "managed" flag at execution time. A per-source PE (CLR header) check is the fallback.
5. For managed tests the VS FQN is the TAEF name unchanged (no '::' to '.' conversion).
6. CommandLineGenerator, the class selection term, and the output parser's fixture-scope logic use '.' when the flag is set.
7. ErrorMessageParser learns .NET exception frames ('   at X[ in file:line N]'). This is managed-only. Today only the first line of an exception message is kept and there is no stack.
8. A managed-only trait filter drops CLR attribute pseudo-properties such as DebuggerStepThroughAttribute, AsyncStateMachineAttribute and ObsoleteAttribute.

**Estimate:** about 11 engineer-days for the .NET Framework (netfx) scope including unit and golden tests, about 0.5 day extra for .NET 6/8/10 (netcore), and about 4 days of optional extras.

- **NAMES-1 Managed TAEF name model in TaefNames**: Add managed-name support without touching the native code path. Option A: overloads GetClassName/GetMethodName/GetBaseName/GetDataSuffix/ToVsFullyQualifiedName(string name, bool isManaged). Option B: a ManagedTaefNames static class; the existing single-argument methods stay native.

Managed rules:
- When the listed class is known (preferred), method = name.Substring(class.Length + 1) up to the first '#', and methodRow = the rest.
- Without the class: no '#' means split at the last '.'. With a '#', treat it as a class row only if the text after it matches ^(metadataSet\d+|\d+)\.[A-Za-z_]\w*(#.*)?$, or if the part before has no '.' (global-namespace data class). Otherwise it is a method row, mirroring the native rule at TaefNames.cs:31-38.
- ToVsFullyQualifiedName for managed is the identity, so rows like '#Weird::Row' and '#a.b c' are kept verbatim.
- The base name for locating sources is '\<classWithoutRow\>.\<method\>'. Keep the CLR arity suffix (`1).

### Risks

- Name ambiguity: data-driven classes with named rows containing '.' ('Edge.Ns.DataClass#a.b c.InClass') cannot be split reliably from the name alone. The native '::' heuristic misreads managed rows containing '::' ('M#Weird::Row' becomes the VS FQN 'M#Weird.Row'). Mitigation: Treat the class listed by TE.exe as authoritative and persist it in TestCaseTaefClassProperty / the VS property. Use the managed name heuristic only as a fallback. Never run native ToVsFullyQualifiedName on managed names.
- Regressing native behaviour or golden files while generalizing '::' handling (16 ScopeSeparator references, 9 TaefNames call sites). Mitigation: Gate every change on an explicit isManaged flag (listing property, test-case property, parser constructor flag). Keep the existing single-argument APIs native-only. ## Audit: detection - Recognizing managed TAEF DLLs, choosing TE.exe (architecture), and choosing the .NET runtime (netfx vs TAEF_CoreCLR)

Today, C# TAEF DLLs are dropped at PeParser.CheckTaefTestDll (DiaResolver/PeParser.cs:342-344, "no 'testdata' section"). The cleanest fix is to extend PeParser's hand-written PE reader rather than take a System.Reflection.Metadata (SRM) dependency. The new code would read the CLI header (data directory 14, CorFlags) and a minimal ECMA-335 #~ table walker up to the AssemblyRef table, then treat any IL DLL that references 'TE.Managed' as a managed TAEF DLL. That is about 300-400 LOC plus tests. The AssemblyRef table also gives the target framework for free: mscorlib 4.0 means netfx, netstandard 2.0 means it runs on the netfx host (verified), and System.Runtime N.0 means .NET N. That avoids decoding TargetFrameworkAttribute. SRM would also work in VS 18: the testhost ships SRM 8.0.0.0 with a 1.0-8.0 redirect. But it adds a deployment variable across VS 2022 builds, devenv and NuGet vstest.console, which a dependency-free reader avoids.

Architecture: AnyCPU must be mapped to the OS architecture (x64 TE.exe on x64), not to x86 as TaefLocator does today. Probes showed that the x86 TE.exe runs AnyCPU tests out-of-proc in a 64-bit TE.ProcessHost (Is64=True). With /inproc (the adapter's debugging path) it runs them 32-bit. So run and debug would use different bitness, and an x86 CoreCLR fails out-of-proc with 0x800700C1.

.NET (Core): injecting TAEF_CoreCLR=\<dotnet root\>\shared\Microsoft.NETCore.App\\<ver\> works:
- Discovery does not need it.
- Roll-forward from 8.0.31 to 10.0.12 works, and a trailing backslash is fine.
- NuGet dependencies copied next to the test DLL load.
- WinForms and WPF types fail: TAEF builds its TPA list from one folder, and pointing it at WindowsDesktop.App fails because there is no coreclr.dll there. This is a hard TAEF limitation.
- The CoreCLR architecture must match the TE.exe process.

The runtime-selection logic itself is about 5-6 days.

Blocker for .NET Core, found empirically and outside the narrow area, so other areas should confirm:
- VSTest will not even hand a net8 TAEF DLL to our adapter. Without Microsoft.NET.Test.Sdk it fails with "Could not find testhost". With Test.Sdk, our net48 adapter from TestAdapterPath is not forwarded to the .NET testhost.
- When the adapter is copied into the output folder it loads, but discovery throws on System.Security.Policy.Zone (System.Security.Permissions is missing), and the 'TaefTestAdapterSettings' settings provider is not found.
- Forcing /Framework:.NETFramework,Version=v4.8 makes the netfx host run our adapter on a net8 DLL; TE.exe was invoked, but our parser reported 0 tests (fact owned by the parsing area).

Totals for this area: netfx about 6 days, netcore about 6 days plus a hosting blocker of 5-10 days that needs a prototype first, tooling about 2 days, optional about 2 days.

## Audit: symbols - Source locations (Test Explorer 'Go To Test' / clickable locations) for managed (C#) TAEF tests

Today's location pipeline only works for C++. TestCaseResolver looks up names like 'Ns::Class::Method' in msdia140 by name and class (UDT). For managed PDBs those lookups always fail. In a Windows (full) managed PDB, DIA has no UDTs and function names are bare ('Passing'). In a portable PDB, msdia140 names functions 'Method.#9'. Lookup by metadata token works for both. I tested three ways to get managed source locations.

(1) VSTest DiaSession: rejected. It reflection-loads the test assembly (ReflectionTypeLoadException on net8, file locking, TE.Managed dependency resolution) and returns sentinel values for async methods. It also needs a declaring type name that we would have to compute from metadata anyway (inherited methods).

(2) Our own System.Reflection.Metadata (SRM) reader: proven by a scratch probe on the net48 portable, net8 portable, embedded-PDB and AnyCPU builds. It needs no assembly load (~80-100 ms per DLL) and resolves every listed TAEF name to the correct file and line, including:
- data-driven rows and data-driven classes
- the global namespace
- nested classes (looked up by simple name)
- generic classes (Foo`1)
- inherited [TestMethod]s (TAEF lists them under the derived class: 'Contoso.Extra.DerivedTests.InheritedMethod'; walk BaseType)
- async methods (via the PDB StateMachineMethod table / GetStateMachineKickoffMethod, or AsyncStateMachineAttribute -\> MoveNext)

(3) Full Windows PDBs: SRM maps names to the MethodDef token, then the adapter's existing msdia140 does IDiaSession.findSymbolByToken + findLinesByRVA. This works, but the first line of an async MoveNext is 0xFEEFEE (16707566), which must be skipped. Then it gives the correct line 63.

Recommendation: hybrid. SRM resolves names to tokens and reads portable/embedded PDBs. DIA-by-token is used only for Windows PDBs. SRM/Immutable are compiled against the 1.6.0/1.5.0 packages but not shipped: the host always has them, because ObjectModel 17.0.0 itself depends on SRM \>= 1.6.0, and testhost.net48 redirects 1.0.0.0-8.0.0.0 -\> 8.0.0.0 in both VS 18 and SDK 10.0.401.

Estimate: ~5 engineer-days for netfx (including unit tests), ~0.25 day extra for netcore (SRM already works on net8 DLLs from a net48 host), ~1-1.5 days of tooling/golden updates, ~1.5 days optional.

## Audit: testhost - VSTest/Visual Studio integration for C# projects and the .NET (Core) test host

## Audit: debugging - Debugging C# TAEF tests from Test Explorer (engines for .NET Framework and CoreCLR hosted by TE.exe)

Today the adapter debugs TE.exe in one of three ways. VsTestFramework uses IFrameworkHandle.LaunchProcessWithDebuggerAttached. Native and ManagedAndNative have the adapter start TE.exe suspended, after which the VS package attaches with exactly ONE engine GUID: NativeOnly or the legacy .NET Framework interop engine ManagedAndNative {92EF0900-...}. The default is Native. TE.exe always gets /inproc and /disableTimeouts while debugging, so TE.ProcessHost child processes never matter.

(a) .NET Framework C# tests: nothing in the debug pipeline is structurally missing.
- ManagedAndNative is already the right engine (mixed mode, which tolerates attaching before the CLR loads).
- VsTestFramework already picks managed engines by itself: I disassembled VS 18 TestWindow.Core and found that DebugLauncher takes its engines from the test container's project, via IDebuggerService.GetDebugTargets / IVsQueryDebuggableProjectCfg. It falls back to ManagedOnly_guid and swaps ManagedOnly and CoreSystemClr by TargetFramework for multi-TFM projects.
- The real gap is the default engine. The default Native engine never binds C# breakpoints, so the adapter must pick the engine per test DLL from the TaefTestType that discovery already reports (Native vs Managed).

(b) CoreCLR tests hosted by TE.exe through TAEF_CoreCLR: the legacy ManagedAndNative GUID only covers .NET Framework. The package must send an engine LIST, [NativeOnly, CoreSystemClr_guid {2E36F1D4-...}], and possibly CoreSystemClr alone. VsDebugTargetInfo4.dwDebugEngineCount is already a count. This needs a new DebuggerEngine value in the WCF contract shared by the adapter and the VSIX package.

ObjectModel 17.0.0 is enough. Even the VS 18.10 ObjectModel offers adapters only IFrameworkHandle.LaunchProcessWithDebuggerAttached and IFrameworkHandle2.AttachDebuggerToProcess(int), with no engine or target-framework parameter. AttachDebuggerInfo.TargetFramework and ITestHostLauncher3 are VS-client-side types that the adapter cannot drive.

Whether each engine combination really works against a suspended TE.exe with a custom-hosted CoreCLR, how /breakOnError (the native int3 in Wex.Logger) behaves under managed engines, AnyCPU on the x86 TE.exe, and ARM64 can only be confirmed by a manual prototype in the VS experimental instance.

### Risks

- The default DebuggerKind is Native, and the Native engine never binds C# breakpoints. Without DBG-2, users who press 'Debug' on a C# TAEF test see tests run but breakpoints silently never hit. Mitigation: Upgrade Native to ManagedAndNative automatically per managed DLL (DBG-2) and log it. This must ship together with managed discovery, not later.
- The legacy ManagedAndNative GUID {92EF0900-...} may not attach the CoreCLR runtime that TE.exe loads itself via coreclr.dll/ICLRRuntimeHost2 with TAEF_CoreCLR. It is also unknown whether [NativeOnly+CoreSystemClr] on a process created suspended (DLO_AttachToSuspendedLaunchProcess) catches the later CoreCLR startup in a custom host, since CoreCLR debugging depends on dbgshim runtime-startup notification. Mitigation: DBG-0 matrix in the experimental instance. If attach-before-load fails for CoreCLR, fall back to resuming TE.exe and attaching the CoreSystemClr engine after coreclr.dll loads; this needs a wait-for-module hook and makes early [AssemblyInitialize] breakpoints unreliable. Add about 1-2 days if so. (needs a prototype)
- /breakOnError: TAEF breaks from native Wex.Logger (IsDebuggerPresent plus a breakpoint). Under a managed-only engine IsDebuggerPresent is false, so it is either a no-op or an unhandled int3 that crashes TE.exe or raises a JIT dialog. Under mixed mode it stops in a native frame (no source) above managed frames. Mitigation: Verify in DBG-0. If managed-only is offered (DBG-4), suppress /breakOnError in CommandLineGenerator.GetBaseCommandLine for that engine, or document the behavior. (needs a prototype)
- With VsTestFramework, VS takes engines from the C# project's F5 debug target. A class-library project may return no targets (VS then falls back to ManagedOnly_guid, which may resolve to the .NET Framework engine for a net8 DLL), and the ManagedOnly to CoreSystemClr swap is only coded for multi-TFM projects. Mitigation: DBG-0 checks what Test Explorer actually picks for single-TFM net8 projects. If wrong, document using Native/ManagedAndNative (extension-installed) for .NET tests, or rely on DBG-5. (needs a prototype)
- WCF contract version skew: adding DebuggerEngine values (DBG-3/DBG-4) means an adapter from the NuGet package that is newer than the installed VSIX can send a value the package cannot deserialize. Mitigation: Append the values only, catch the fault in MessageBasedDebuggerAttacher with an actionable message, and keep netfx managed debugging on the existing ManagedAndNative value so it needs no contract change.
- AnyCPU managed DLLs run under the x86 TE.exe (fact 3), so mixed-mode debugging happens in a 32-bit process. ARM64 mixed-mode (interop) debugging support for .NET Framework 4.8.1 and CoreCLR in VS is unverified. Mitigation: Include AnyCPU/x86 in the DBG-0 matrix. Test ARM64 only if hardware is available; otherwise document it as unsupported and offer the managed-only engine (DBG-4). (needs a prototype)
- Mixed-mode (interop) debugging is noticeably slower and disables some managed features (e.g. Edit and Continue limits), which may annoy C# users. Mitigation: DBG-4 offers a managed-only choice once DBG-0 confirms it works.

1. SRM vs a hand-written metadata reader. The detection audit (RT-1) avoids SRM; the symbols audit (LOC-1) adopts it as host-provided. Pick one. If SRM is used, RT-1 drops from 3 days to about 1, and a try/catch fallback is needed for hosts without SRM. VS 2022 availability is unverified.
2. C# template test-container mechanism. Tooling T1 relies on a bare ProjectCapability TestContainer; the testhost audit assumes Microsoft.NET.Test.Sdk. A 0.5-day IDE prototype decides it.
3. NuGet layout. VS-1 uses build/net462 + buildTransitive; T5 uses build/netstandard2.0.
4. Some audits (debugging, tooling O2) still assume AnyCPU runs under the x86 TE.exe. The detection audit shows this must change (RT-3) because run and debug bitness differ. RT-3 must ship in netfx.

**After removing duplicates:**
- netfx minimum is roughly 25-30 engineer-days (names ~10, detection with SRM ~4, locations ~5, debugging including the prototype ~3.5, NuGet/E2E ~2.5, consolidated samples/goldens ~5, plus ~3.5 for the missing areas above).
- Tooling is ~7-8 days (templates 5, docs 2, metadata/version 1).
- netcore is ~15-20 days on top: runtime selection ~4, hosting ~6-8 after a mandatory Test Explorer prototype, CoreCLR debugging 2-3, net8 template/sample ~3.

The single largest uncertainty is netcore hosting: the dotnet testhost never sees VSIX adapters, and the adapter needs fixes to load in .NET 8. It should be prototyped in VS Test Explorer, not only vstest.console, before any netcore commitment.

### Missing areas

- Settings helper files (.taef_settings_helper) are written by a C++ post-build step (SampleTests/HelperFileTests/HelperFileTests.vcxproj:92) and documented for C++ only (README.md:471). No audit covers the C# equivalent, an MSBuild target in the C# template/props or a documented snippet that writes $(TargetPath).taef_settings_helper. Suggested: Add a WriteTaefSettingsHelper target to the C# template (or the NuGet build props), plus a README snippet and a HelperFileTests C# sample case (0.5 days, tooling)
- Crash handling for managed tests is not sized. The native samples have HardCrashingSampleTests golden files, but nobody probed managed hard crashes: StackOverflowException, Environment.FailFast, an unhandled exception on a background thread, or an AccessViolation through P/Invoke. Each of these kills TE.exe or TE.ProcessHost. Also unsized is how StreamingTaefOutputParser and MissingTestsReportMode attribute the crash. Suggested: Add crashing managed test methods to the managed sample, record the TE.exe output (out-of-proc and /inproc), and add parser tests plus one golden file (1 days, netfx)
- IsolationLevel (/isolationLevel Class/Method/Test) and RunInProcess with managed DLLs are not probed. Only the default and /inproc were run. Managed class isolation spawns a TE.ProcessHost per class with its own CLR. Suggested: Probe /isolationLevel:Class and Method on the net48 and net8 (TAEF_CoreCLR) samples. Check that TAEF_CoreCLR propagates to child hosts and that fixture output is attributed correctly. Add a golden row. (0.5 days, netfx)
- Existing users get a behavior change. Once DLLs that reference TE.Managed are detected, any helper or utility library in a C++ solution that references TE.Managed (without [TestClass]) now starts TE.exe during discovery. That costs about 200 ms per DLL, and Test Explorer may surface new tests. No audit proposes an opt-out setting. Suggested: Add option 'Discover managed (C#) TAEF tests' (default on), plumbed through RunSettings.cs, ITaefTestAdapterSettings, SettingsWrapper, TaefTestAdapterSettings.xsd, the options page and SettingsPrinter, with golden settings updates (0.75 days, optional)
- Each audit adds new options in isolation: the RT-3 AnyCPU architecture, the RT-7/VS-7 runtime, NAMES-O2 traits and DBG-4 Managed. Nobody sizes the shared settings plumbing once: XSD enum/elements, RunSettings and the GetUnsetValuesFrom merge, the VsPackage options pages (TestExecutionOptionsDialogPage and OptionsPagesTests), SettingsPrinter output, PlaceholderReplacer, the README option table, and the golden settings files. Suggested: One consolidated settings work item for all new managed options, with XSD and options-page tests (1.5 days, netfx)
- C++/CLI (mixed-mode) TAEF DLLs are an open question in three audits but have no work item. Such a DLL has both a CLI header and possibly a 'testdata' section, and the naming (Native or Managed, '::' or '.') is unknown. Suggested: Build a /clr TAEF probe that uses the native macros and, separately, one that uses managed [TestClass]. Record /listProperties output and PE traits, and add a regression test that pins the chosen classification. (0.5 days, netfx)
- Data files of managed [DataSource("Table:x.xml#...")] tests must sit next to the DLL or in the working directory. Templates and samples need CopyToOutputDirectory, and the troubleshooting docs need the 'Failed to find the data source' (#error Blocked) case. Not covered beyond the parser handling. Suggested: Template/sample CopyToOutputDirectory items plus a README troubleshooting entry (0.25 days, tooling)
- Security review of the new code paths is absent. Two items are new: a hand-written ECMA-335 parser (RT-1) and SRM (LOC-1), both reading untrusted PE/PDB files during discovery. The audits also leave unanswered whether TE.exe /listProperties runs managed static constructors or module initializers during discovery; the native analogue is DllMain. If it does, the origin check must stay, with no regression when Zone is replaced (VS-3). Suggested: Threat-model note, malformed/truncated PE and PDB fuzz tests for the metadata reader, and a probe of whether listing runs module initializers (1 days, netfx)
- Licensing and redistribution are not reviewed. The SRM/Immutable fallback shipping in LOC-4 is MIT and fine. However, samples, templates and CI reference WDK TE.Managed reference assemblies, which must not be checked in or redistributed. Also, a NuGet package with build props must not pull TAEF runtime files (e.g. TE.TestAdapter.dll) into outputs. Suggested: Redistribution checklist: verify package contents tests assert no WEX/TE binaries; document that WDK is required (0.25 days, tooling)
- Test Explorer hierarchy and grouping for dotted managed FQNs is only covered as optional (NAMES-O1). The audits do not note that VS splits on the last '.', which gives correct Namespace/Class/Method for ordinary managed tests. Only rows containing '.' and data-driven class rows ('Ns.Class#metadataSet0.M') are mis-grouped. Separately, the 'TestCase.Hierarchy' property can be registered by string id even with ObjectModel 17.0.0. Suggested: Fold into NAMES-O1: prototype the Hierarchy property (registered by id) against the ManagedType/ManagedMethod approach in VS 2022 and 2026 (0.5 days, optional)
- Code coverage is unaddressed. Microsoft.NET.Test.Sdk adds the CodeCoverage shim, and users of C# test projects expect 'Analyze Code Coverage' to work. Tests actually run in the TE.exe child process, so coverage of them is unknown. Suggested: Document as unsupported, or probe the VS dynamic coverage child-process collection with TE.exe (0.5 days, optional)
- The test durations, scheduling and parallel splitting files are keyed by FullyQualifiedName (the TAEF name) and Source. Nothing needs to change, but no audit adds a regression test showing that the *.taef.testdurations round trip and ParallelTestRunner splitting work with dotted names and mixed native and managed sources. Suggested: Add one TestDurationSerializer and ParallelTestRunner test with managed names (0.25 days, netfx)
